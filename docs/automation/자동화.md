# 자동화

> 최종 확인: 2026-08-11

혼자서 앱을 여러 개 굴리면 개발 시간보다 **운영 시간**이 먼저 한계에 부딪힙니다. 앱이 늘어날수록 릴리스, 스토어 확인, 리뷰 확인, 지표 확인이 선형으로 늘어납니다. 자동화의 목적은 개발을 빠르게 하는 게 아니라 **앱 개수가 늘어도 운영 시간이 늘지 않게 만드는 것**입니다.

## 무엇을 자동화하면 실제로 이득인가

기준은 단순합니다. **앱 개수에 비례해서 늘어나는 일**이면 자동화 가치가 있고, 한 번만 하는 일이면 없습니다.

### 이득이 큰 것들

**1. 릴리스 파이프라인**
빌드, 서명, 버전 올리기, 태그 만들기, 스토어 업로드. 앱마다 반복되고, 손으로 하면 반드시 어느 단계를 빠뜨립니다. 버전 번호를 올리는 것을 시작점으로 삼고 나머지를 자동으로 따라오게 만드는 구조가 관리하기 편합니다.

**2. 리뷰 수집**
여러 앱의 스토어 리뷰를 매일 모아서 한 번에 보는 것. 스토어 콘솔을 앱마다 들어가는 건 앱이 세 개만 넘어도 안 하게 됩니다. 안 보게 되면 평점이 떨어지는 걸 몇 주 뒤에 압니다.

**3. 크래시·ANR 감시**
새 버전을 낸 뒤 크래시율이 튀는 걸 자동으로 잡는 것. 이건 시간 절약이 아니라 **손실 방지**입니다. 나쁜 릴리스를 며칠 방치하면 평점이 영구적으로 깎입니다.

**4. 수익·지표 다이제스트**
매일 또는 매주 앱별 수익과 주요 지표를 한 장으로 받아 보는 것. 대시보드를 들어가서 보는 것과 알아서 오는 것은 실제로 보는 빈도가 완전히 다릅니다.

**5. 스토어 상태 확인**
심사 상태, 정책 경고, 배포 단계 변화. 심사가 반려됐는데 일주일 뒤에 아는 상황을 막습니다.

### 자동화 가치가 낮은 것들

- 처음 한 번 하는 설정 (계정 만들기, 첫 스토어 등록). 자동화 스크립트 만드는 시간이 더 깁니다.
- 자주 안 바뀌는 것. 1년에 한 번 하는 일은 그냥 문서로 적어 두세요.
- 매번 판단이 필요한 일. 판단을 자동화하려 들면 아래 문제로 갑니다.

## 절대 자동화하면 안 되는 것

### 돈이 나가는 방향의 결정

**광고비 증액을 자동화하지 마세요.** 성과가 좋아 보이면 예산을 올리는 규칙은 만들기 쉽고 위험합니다.

- 지표가 좋아 보이는 이유가 측정 오류일 수 있습니다.
- 수익은 며칠 뒤에 들어오고 광고비는 지금 나갑니다. 자동 증액은 그 시차 위에서 돕니다.
- 사람이 자는 동안 돌아갑니다.

돈이 나가는 방향은 **줄이는 것만 자동화하고 늘리는 것은 사람이** 하세요. 상한선(하루, 월 단위)은 자동으로 강제하고, 그 위로 올리는 건 손으로.

### 사용자에게 직접 나가는 것

푸시 알림, 리뷰 답글, 이메일. 초안까지는 자동으로 만들되 발송은 확인 후에 하세요. 잘못 나간 푸시는 회수가 안 되고, 대량 발송은 그대로 대량 사고가 됩니다.

### 되돌릴 수 없는 것

프로덕션 배포, 데이터 삭제, 스토어 제출. 자동화하더라도 마지막 실행은 명시적인 트리거로 두세요.

## 자동화의 전제: 실패가 보여야 합니다

**조용히 죽은 자동화가 자동화 없는 것보다 나쁩니다.** 없으면 직접 확인이라도 하는데, 있다고 믿으면 아무도 안 봅니다.

크론이나 스케줄 작업을 만들 때 같이 만들어야 하는 것들입니다.

1. **실패 시 알림**. 실행 중 에러가 나면 어딘가로 반드시 전달되어야 합니다.
2. **안 돌았을 때의 알림**. 이게 빠지기 쉽습니다. 작업이 아예 실행되지 않은 경우는 에러도 안 납니다. "마지막 성공 시각"을 기록하고, 예상 주기를 넘기면 알리세요.
3. **결과 확인**. 성공 코드만 보지 말고 실제로 원하는 상태가 됐는지 한 건을 다시 읽어 확인하세요.

## 알림 설계: 읽히는 알림만 알림입니다

자동화가 늘면 알림도 늘고, 알림이 늘면 안 보게 됩니다. 그러면 정작 중요한 알림도 묻힙니다.

- **목적별로 채널을 나누세요.** 긴급(사용자 영향 있음)과 참고(일일 리포트)를 같은 곳에 보내면 둘 다 안 읽힙니다.
- **같은 원인의 반복은 한 번만** 알리세요. 같은 에러가 5분마다 오면 채널을 음소거하게 됩니다.
- **깜빡임을 막으세요.** 상태가 왔다 갔다 하는 경우, 두 번 연속 같은 상태일 때만 알리는 식으로 완충을 두면 알림 수가 크게 줄어듭니다.

### 알림 본문은 평문으로 쓰세요

디스코드, 슬랙, 텔레그램으로 알림을 보낼 때 마크다운을 쓰기 쉬운데, **휴대폰 잠금화면의 푸시 미리보기는 마크다운을 렌더링하지 않습니다.** 별표와 백틱이 그대로 문자로 보입니다.

```
🟢 **앱 이름** - 배포 완료          <- 잠금화면에 이렇게 그대로 보입니다
`com.example.app` v1.2
```

대부분의 알림은 열어 보지 않고 미리보기만 읽고 넘어갑니다. 그 미리보기가 실제 화면이라고 생각하고 쓰세요.

- 표를 쓰지 마세요. 마크다운 표는 렌더링되지 않거나, 되더라도 모바일에서 셀 중간에 줄바꿈되어 읽을 수 없게 됩니다. 항목별로 짧은 제목 줄 + 하이픈 목록으로 쓰세요.
- 강조는 이모지로 하세요. 이모지는 어디서나 렌더링됩니다.
- 가장 중요한 정보를 첫 줄에 넣으세요.

## AI를 자동화에 쓸 때

에이전트에게 운영 작업을 맡길 수 있게 되면서 자동화의 범위가 넓어졌습니다. 다만 경계가 필요합니다.

**적합한 일**
- 여러 소스의 데이터를 모아 사람이 읽을 요약으로 만들기
- 리뷰나 피드백을 분류하고 답변 초안 만들기
- 로그에서 이상 패턴 찾아 보고하기
- 반복 작업의 절차를 고정된 명령으로 만들어 두기

**맡기면 안 되는 일**
- 판단해서 돈을 쓰는 것
- 확인 없이 사용자에게 나가는 것
- 되돌릴 수 없는 실행

원칙 하나로 정리하면 이렇습니다. **모델은 제안하고, 코드가 강제합니다.** 조건 판단은 모델에게 맡겨도 되지만, "이 조건에서는 절대 실행하지 않는다"는 코드로 막아 두세요. 프롬프트에 적은 금지는 언젠가 넘어갑니다.

## 어디서부터 시작할까

앱이 한두 개라면 자동화보다 앱을 하나 더 만드는 게 낫습니다. 아래 순서를 권합니다.

1. **앱 3개쯤**: 릴리스 스크립트 하나. 손으로 하던 빌드·업로드 절차를 그대로 스크립트로 옮기는 것부터.
2. **앱 5개쯤**: 리뷰와 크래시 알림. 이때부터 스토어 콘솔을 앱마다 들어가는 게 불가능해집니다.
3. **앱 10개쯤**: 수익 다이제스트, 스토어 상태 감시. 그리고 이 시점에는 위의 "실패가 보이는가"를 반드시 갖추세요.

새 앱을 만들 때 자동화가 자동으로 따라오게 만드는 게 핵심입니다. **앱 목록을 어딘가에 등록하고 자동화가 그 목록을 순회하게** 하세요. 앱마다 설정을 복사하는 구조면 새 앱은 언제나 빠집니다.
