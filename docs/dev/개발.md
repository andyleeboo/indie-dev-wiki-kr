# 개발

> 최종 확인: 2026-08-11

1인 개발에서 개발 단계의 병목은 이제 "코드를 얼마나 빨리 쓰느냐"가 아닙니다. AI 코딩 도구가 그 부분을 상당히 가져갔습니다. 남은 병목은 **혼자서 여러 개를 동시에 굴릴 때 품질이 무너지지 않게 하는 것**입니다. 이 문서는 그 관점에서 정리했습니다.

## MVP: 최소 기능이 아니라 최소 검증

MVP를 "기능을 줄인 버전"으로 이해하면 대개 실패합니다. 기능만 줄어든 앱은 그냥 부실한 앱입니다.

**MVP는 검증하려는 가설이 하나 있고, 그 가설을 확인하는 데 필요한 것만 만든 버전입니다.**

- 가설: "사람들은 이 문제를 겪고 있고, 이런 방식이면 돈이나 시간을 쓸 것이다"
- 그 가설을 확인하는 데 필요 없는 것: 회원가입, 설정 화면, 다크 모드, 온보딩 튜토리얼

특히 1인 개발에서 초기에 만들지 말아야 할 것들이 있습니다.

- **로그인·회원가입**: 필요해질 때까지 미루세요. 로그인은 그 자체가 이탈 지점이고, 개인정보 처리 의무를 즉시 발생시킵니다.
- **자체 백엔드**: 기기 안에서 되는 일이면 서버를 두지 마세요. 서버가 생기는 순간 운영, 비용, 장애, 개인정보가 전부 따라옵니다.
- **설정 화면**: 설정이 필요하다는 건 기본값을 못 정했다는 뜻인 경우가 많습니다.

## AI 에이전트와 함께 개발하기

2026년 기준으로 코딩 에이전트는 자동완성 도구가 아니라 **여러 파일을 읽고 고치고 명령을 실행하는 실행 주체**입니다. 이 전제가 바뀌면 작업 방식이 바뀝니다.

### 규칙은 문서가 아니라 게이트로 만들어야 지켜집니다

이게 이 문서에서 가장 중요한 한 줄입니다.

에이전트에게 규칙 파일(`CLAUDE.md`, `AGENTS.md` 등)로 "이렇게 해라"를 적어 두면 대체로 따릅니다. 그런데 **대체로**입니다. 컨텍스트가 길어지거나 급한 작업이 끼면 조용히 어겨집니다. 사람도 똑같습니다. 며칠 지나면 자기가 적어 둔 규칙을 잊습니다.

그래서 중요한 규칙일수록 **글이 아니라 실행을 막는 장치**로 만들어야 합니다.

| 규칙 | 문서에만 적으면 | 게이트로 만들면 |
|---|---|---|
| 테스트 광고 ID로 릴리스하지 않기 | 언젠가 사고가 납니다 | 릴리스 빌드에 테스트 ID가 있으면 빌드 실패 |
| 릴리스 전 빌드·린트 통과 | 급하면 건너뜁니다 | 푸시 전 훅에서 자동 실행 |
| 개인정보 처리방침 URL이 살아 있는지 | 확인을 잊습니다 | 제출 스크립트가 URL을 열어 보고 실패 처리 |
| 메인 브랜치에 직접 커밋 금지 | 가끔 합니다 | 훅에서 차단 |

구현은 거창할 필요가 없습니다. git 훅(`core.hooksPath`로 저장소 안의 디렉터리를 지정), 빌드 스크립트 한 줄, CI 잡 하나면 됩니다. **규칙을 하나 만들 때마다 "이걸 어기면 무엇이 막히는가"를 같이 정하세요.** 답이 "아무것도"라면 그건 규칙이 아니라 희망입니다.

### 규칙 파일에 무엇을 적을 것인가

에이전트용 규칙 파일은 길수록 좋지 않습니다. 매 세션 컨텍스트를 차지하고, 길어지면 지켜지는 비율이 떨어집니다.

- **하드 규칙만** 적으세요. 어기면 사고가 나는 것들.
- 배경 설명, 참고 자료는 별도 문서로 빼고 링크만 두세요. 필요할 때 읽게 하면 됩니다.
- 프로젝트마다 다른 규칙은 그 프로젝트 폴더에 두세요.
- "이 저장소에서 절대 하면 안 되는 것" 목록이 가장 값어치가 높습니다.

### 여러 작업을 동시에 굴릴 때는 worktree

에이전트에게 작업을 시켜 놓고 기다리는 시간이 아깝다고 다른 작업을 같은 폴더에서 시작하면 충돌합니다.

`git worktree`를 쓰면 같은 저장소를 여러 폴더에 동시에 체크아웃할 수 있습니다. 브랜치별로 폴더가 하나씩 생기므로 서로 간섭하지 않습니다.

```bash
git worktree add ../myapp-feature-a -b feature-a
```

주의할 점 하나: **worktree는 gitignore된 파일을 공유하지 않습니다.** `google-services.json`, `local.properties`, `.env`, `GoogleService-Info.plist` 같은 파일은 새 worktree에 없어서 첫 빌드가 실패합니다. 원래 체크아웃에서 복사해 오는 스크립트를 하나 만들어 두면 매번 헤매지 않습니다.

작업이 끝나면 정리하세요. 안 지우면 오래된 worktree가 쌓이고, **엉뚱한 폴더에서 빌드해서 옛날 코드를 테스트하는 사고**가 납니다.

### 1인 팀에서 CI는 로컬 우선이 빠릅니다

GitHub Actions 같은 원격 CI는 팀 협업 전제로 설계돼 있습니다. 1인 개발에서는 푸시하고 결과를 기다리는 왕복 시간이 그대로 손해입니다.

**푸시 전 훅에서 검사를 돌리는 쪽**이 대체로 낫습니다.

- 실패를 몇 초 만에 알 수 있습니다.
- 무료 실행 시간 한도를 신경 쓸 필요가 없습니다.
- 바뀐 경로에 해당하는 검사만 골라 돌리면 더 빨라집니다.

원격 CI가 여전히 필요한 경우는 릴리스 빌드, 스토어 업로드처럼 **재현 가능한 환경이 중요한 작업**입니다. 일상적인 린트와 테스트는 로컬에서 막는 게 효율적입니다.

한 가지 함정: 로컬 검사는 우회하기 쉽습니다(`--no-verify`). **급할 때 건너뛴 검사가 그대로 배포되는 게 이 방식의 유일한 약점**이므로, 우회했으면 그 사실이 어딘가에 남게 만드세요.

## 에이전트가 쓴 코드에서 반복해서 나오는 사고

에이전트가 만든 코드는 컴파일도 되고 그럴듯해 보이지만, 다음 유형은 검토에서 잡아야 합니다.

### 1. 서버가 준 에러 메시지를 사용자 화면에 그대로 띄우기

`e.message`, `error.toString()`, HTTP 응답 본문을 그대로 화면에 출력하는 코드가 정말 자주 나옵니다. 에러 처리를 시키면 가장 짧은 정답이 그것이기 때문입니다.

문제는 그게 나가는 순간입니다. 사용자는 `400 INVALID_ARGUMENT {"error":{"details":...}}` 같은 문자열을 보게 되고, 진짜 원인(예: 이 빌드에 API 키가 안 들어감)은 아무도 모릅니다. 내부 구조나 키 이름이 노출되기도 합니다.

**원문은 로그로 보내고, 화면에는 사람이 쓴 문장을 띄우세요.** 그리고 필요한 자격증명이 없으면 호출 자체를 하지 말고 명확히 실패시키세요. 400 응답이 설명을 대신하게 두면 안 됩니다.

### 2. 로컬과 원격을 헷갈린 채 "성공"으로 보고하기

로컬 시뮬레이터와 실제 환경을 모두 다루는 CLI에서 자주 터집니다. 대표적으로 Cloudflare의 `wrangler`는 `d1 execute`, `r2 object put` 등이 **기본적으로 로컬 상태를 대상으로 동작합니다.** `--remote`를 붙이지 않으면 명령은 성공했다고 나오고 프로덕션에는 아무 일도 일어나지 않습니다.

아무 에러도 안 나기 때문에 발견이 늦습니다. "데이터를 넣었는데 서비스에 안 보인다"로 며칠을 태울 수 있습니다.

일반화하면 이렇습니다. **쓰기 명령을 실행한 뒤에는 반드시 한 건을 다시 읽어서 확인하세요.** 그리고 대상이 로컬인지 원격인지 명시하는 플래그를 습관적으로 붙이세요.

### 3. 오래된 빌드를 테스트하기

빌드와 설치가 실제로 됐는지 확인하지 않고 테스트에 들어가면, 이전 빌드를 붙잡고 "고쳐지지 않았다"를 반복하게 됩니다.

- Android: `adb shell dumpsys package <패키지명> | grep versionCode` 로 기기에 깔린 버전을 확인
- 스크립트가 폴더 이동에 실패했는데 뒤 명령이 그대로 실행되는 경우가 있으니, 셸 스크립트에는 `set -e`를 넣으세요.

### 4. 빈 결과를 "없음"으로 결론 내리기

이건 [데이터·분석](데이터분석.md) 문서에서 자세히 다룹니다. 요약하면, 쿼리나 CLI가 빈 결과를 돌려줬을 때 대부분의 원인은 필터이지 시스템이 아닙니다.

## 기술 스택: 1인 개발자의 현실적인 선택

### 원칙

- **운영 부담이 적은 쪽**을 고르세요. 성능이나 유행이 아닙니다. 새벽에 서버가 죽으면 일으킬 사람이 본인 한 명입니다.
- **관리형 서비스**를 최대한 쓰세요. 직접 운영하는 서버 하나가 앱 세 개보다 시간을 많이 먹습니다.
- **기기 안에서 되는 일은 기기 안에서** 하세요. 서버를 안 두는 게 가장 싼 아키텍처입니다.

### 무료 티어로 어디까지 가는가

초기에는 무료 티어로 충분히 굴러갑니다. 한도를 알고 설계하면 비용이 0에서 시작합니다.

**Cloudflare Workers (무료)**
- 요청: 하루 100,000건 (UTC 자정 리셋, 초과 시 에러 1027)
- CPU 시간: 요청당 10ms
- Worker 개수: 100개
- 요청당 서브리퀘스트: 50건

**Cloudflare D1 (무료)**
- 읽기: 하루 500만 행
- 쓰기: 하루 10만 행
- 저장 용량: 총 5GB

숫자를 보면 감이 옵니다. **간단한 API 백엔드, 설정 원격 제어, 랭킹 저장, 콘텐츠 캐시 정도는 무료 티어 안에서 충분히 돌아갑니다.** 하루 10만 요청은 개인 앱 여러 개를 합쳐도 쉽게 안 넘습니다.

다만 CPU 10ms는 빡빡합니다. 무거운 연산은 무료 티어에서 안 됩니다. 이런 구조가 유리합니다.

- 계산은 미리 해서 저장해 두고, 요청 시에는 읽기만 하기
- 외부 API 응답을 그대로 중계하지 말고 주기적으로 가져와 저장해 두기 (외부 API가 죽어도 앱은 살아 있습니다)

Firebase도 무료 티어(Spark)로 Analytics, Crashlytics, 원격 구성, 푸시를 쓸 수 있습니다. 한도는 서비스마다 다르므로 공식 요금 페이지에서 확인하세요.

### 원격으로 끌 수 있게 만들어 두기

앱은 배포하면 되돌리기 어렵습니다. 심사를 다시 받아야 하고, 사용자가 업데이트를 안 하면 옛 버전이 계속 돕니다.

그래서 **위험한 기능은 서버에서 끌 수 있게 만들어 두세요.** Firebase 원격 구성이나 직접 만든 설정 API로 충분합니다.

- 광고 표시 여부와 빈도
- 새 기능 노출 여부
- 외부 API 호출 여부 (상대가 죽었을 때 끄기)

이 장치 하나가 "긴급 업데이트를 심사 넣고 며칠 기다리기"를 막아 줍니다. 실제로 가장 자주 쓰게 되는 안전장치입니다.
